# Plan: Magic Code Login — Concrete Fix (post-source-review)

## Summary
The deployed `student-login` Edge Function source has been retrieved and reviewed. Six concrete bugs and scaling issues are visible in the code; we still need three short DB queries to confirm which one(s) are actually causing "many codes failing", but the fix is the same for almost all of them. This plan replaces the earlier diagnostic-only plan now that we know what the function does.

Source archived at [`.claude/PRPs/notes/student-login.deployed-source.ts`](../notes/student-login.deployed-source.ts).

## User Story
As a Hanguk student receiving a magic access code from my counselor,
I want my code to log me in reliably forever (until my account is disabled),
so that I never have to call my counselor when the system rejects me.

## Confirmed answers (from user)
- Codes are **reusable forever** (not one-time use)
- Codes are **permanent per student** (never regenerated by CRM)
- We **don't have one specific failing code** to test with — many are failing
- The Edge Function source — **now in hand** at the notes path above

## What the deployed `student-login` actually does

```
1. Read magicCode from request body
2. Normalise: trim().toUpperCase().replace(/\s+/g, '')   ← matches client ✓
3. Look up profiles WHERE magic_code = normalised, .maybeSingle()
4. Reject staff roles
5. Find the auth.users row by:
   a. auth.admin.getUserById(profile.user_id)       ← O(1)
   b. fall back: paginated listUsers, search for email "student-{profile.user_id}@hanguk.local"   ← O(N/1000)
6. If no auth user found, auth.admin.createUser({email: "student-{profile.user_id}@hanguk.local",
                                                 password: "student-{profile.user_id}-hanguk-A1!"})
7. signInWithPassword(email, password) using "stable" password derived from CURRENT profile.user_id
8. On wrong-password, admin.updateUserById(password=stable), then retry signIn
9. Return {access_token, refresh_token, expires_in, expires_at, token_type, user, profile}
```

## Six concrete bugs / smells visible in the source

### Bug A — `createUser` race condition leaves a permanently-broken student
- Two near-simultaneous requests with the same magic code (or a rapid double-click) both reach line 134 `auth.admin.createUser(...)`.
- One succeeds; the other fails with **"email already exists"** (deterministic email is the same).
- The losing request returns **"Failed to create session"** (line 148) but **does not delete the orphan profile.user_id pointer**, and **does not re-attempt sign-in with the now-existing user**.
- Future logins for that student go through the existing-user branch and *should* work, but **only if the trigger updated `profile.user_id` to the winning auth user's id**. If it didn't (or if the loser's request landed first and partially mutated state), `profile.user_id` becomes a permanent ghost.
- **Severity: High.** Likely explains a chunk of the "many failing".

### Bug B — `listUsers` pagination scales as O(N) per login
- Lines 100-119 walk the entire `auth.users` table 1000 rows at a time, just to find one email.
- For a project with 5 000 users that's 5 round-trips per cold-path login (~2-5s extra).
- For 10 000 users it can hit the Edge Function's wall-clock timeout (~60s) — function dies with NO error to the client, who sees the generic "Login failed".
- **Severity: High** if the project has grown past ~3 000 students. Confirm via Bug F query #3.

### Bug C — Client `setSession` is given only the refresh token
- Edge Function returns `{access_token, refresh_token, expires_in, expires_at, token_type}` (lines 262-268) — full session.
- Dart client at [`auth_repository.dart:97-99`](../../../lib/features/auth/data/auth_repository.dart#L97) calls `_auth.setSession(session['refresh_token'].toString())` — refresh-token-only signature.
- This forces the SDK to round-trip back to the gotrue server to *exchange* the refresh token for an access token. If the gotrue server has already rotated the refresh token (because step 7 of the Edge Function consumed it), the second exchange fails and the user sees "Login failed."
- **Severity: Medium-High.** Plausibly explains intermittent "code didn't work even though counsellor swears it's right" reports.

### Bug D — Stable-password drift causes a forced password reset on every login except the first
- Line 126: `stablePassword = student-${profile.user_id}-hanguk-A1!` — built from CURRENT `profile.user_id`.
- On first login, `profile.user_id` is the placeholder UUID set by the CRM. Auth user is created with that placeholder-derived password.
- A trigger then updates `profile.user_id` to the new auth user's UUID (different).
- On every subsequent login, line 126 builds a different password (because `profile.user_id` changed). `signInWithPassword` fails. Function falls into the reset path (line 215-244). It works, but it hammers `auth.admin.updateUserById` once per login per student.
- **Severity: Medium.** Functionally OK for the student (login still succeeds via the reset retry), but burns auth admin API quota and adds latency.

### Bug E — Generic error messages hide the real failure
- Function returns `'Invalid code. Please check and try again.'` (line 55) for code-not-found, but the same string-shape `'Failed to create session'` for auth-create errors and `'Failed to verify code'` for DB errors.
- Client at [`auth_repository.dart:88-91`](../../../lib/features/auth/data/auth_repository.dart#L88) just shows whatever the error string is.
- A counselor receiving a "Login failed" report can't tell whether the code is wrong, the student is missing an auth row, or the function timed out.
- **Severity: Medium.** Not a direct cause of failures but actively prevents diagnosis.

### Bug F — Data-integrity questions still open (3 SQL queries pending)
We need to confirm the data shape before deploying any fix:
1. `select count(*) from profiles where magic_code is null` — how many students have no code at all?
2. `select magic_code, count(*) from profiles where magic_code is not null group by magic_code having count(*) > 1` — duplicate codes?
3. `select count(*) from auth.users` — for Bug B scaling concern.
4. `select count(*) from profiles p left join auth.users u on u.id = p.user_id where u.id is null and p.magic_code is not null` — orphan profile.user_id pointers.

## Risk Register

| Risk | Why it matters | Mitigation |
|---|---|---|
| **Replacing `student-login` could break currently-working students** | Many students are currently logging in fine | Deploy fixed function under a NEW slug (`student-login-v2`), point the client at it via a feature flag, keep `student-login` as-is for rollback. After 48h with green metrics, retire v1. |
| **Migration of orphan profiles requires care** | We may need to bulk-fix `profile.user_id` rows to point at the right `auth.users` rows | One-shot SQL run, scripted, with a `dry_run = true` mode that prints intended updates first. Confirm count before running for real. |
| **Hardcoded password pattern in source** | `student-{uuid}-hanguk-A1!` is partially predictable but mitigated by uuid being non-guessable | Not changing in this plan — it's not a security issue (auth uses bcrypt-style hashing); changing the pattern would force a re-reset for every student |
| **Rotating refresh token consumed by client `setSession`** | Bug C — the refresh-token-only path is fragile | Pass the full session object to `setSession` instead. The Dart SDK supports this since gotrue 2.0+ |
| **Scaling fix introduces a new index** | Index creation on auth.users (managed by Supabase) is not allowed | The fix doesn't need an index on auth.users — it stops calling listUsers entirely by storing a stable email lookup alongside profile.user_id |

### Task 1 — Author `student-login-v2` Edge Function (the real fix)

Create [`.claude/PRPs/notes/student-login.v2.ts`](../notes/student-login.v2.ts) with the following changes vs. the current source:

#### 1A. Eliminate `listUsers` pagination
Add a column `auth_email` (or reuse a column the trigger already writes) on `profiles` that stores the deterministic email when the auth user is created. Lookup becomes O(1) via:
```ts
const { data: profile } = await supabaseAdmin
  .from('profiles')
  .select('id, user_id, auth_email, full_name, magic_code')
  .eq('magic_code', normalizedCode)
  .maybeSingle();

// then:
const email = profile.auth_email ?? `student-${profile.user_id}@hanguk.local`;
const { data: existingUser } = await supabaseAdmin.auth.admin.getUserById(profile.user_id);
```
If `existingUser` is null AND `profile.auth_email` is set, look up by email via `getUserByEmail()` (also O(1)) — only fall back to the paginated listUsers if both fail.

#### 1B. Fix the createUser race
Wrap step 6 in a try/catch on the "duplicate email" error. On failure, immediately re-look-up the existing auth user (someone else created it in parallel) and continue from step 7.

#### 1C. Stop password drift
Move the `stablePassword` derivation **after** the existingUser lookup, and base it on the CONFIRMED auth-user id (not `profile.user_id` which may have drifted):
```ts
const userIdForPassword = existingUser?.id ?? profile.user_id;
const stablePassword = `student-${userIdForPassword}-hanguk-A1!`;
```
Result: subsequent logins find the same password; no more reset round-trip.

#### 1D. Typed error codes
Replace every `JSON.stringify({ error: '<message>' })` with:
```ts
JSON.stringify({ error: 'CODE_NOT_FOUND' | 'CODE_LOOKUP_FAILED' | 'STAFF_BLOCKED' | 'AUTH_CREATE_FAILED' | 'AUTH_SIGNIN_FAILED' | 'INTERNAL_ERROR', detail: '...' })
```

#### 1E. Structured logging
Single JSON log line per request: `{ts, code_mask, result: 'OK'|'<ERROR_CODE>', branch: 'created'|'existing'|'reset', durationMs}`. Filter on `result != 'OK'` for instant diagnosis.

### Task 4 — DB diagnostic view (counselor self-serve)

Create migration `supabase/migrations/<ts>_student_code_diagnostic_view.sql`:
```sql
create or replace view public.student_code_status as
select
  p.id as profile_id,
  p.full_name,
  p.magic_code,
  p.user_id as profile_user_id,
  u.id as auth_user_id,
  u.email as auth_email,
  u.banned_until,
  u.deleted_at,
  case
    when p.magic_code is null then 'NO_CODE'
    when u.id is null then 'AUTH_USER_MISSING'
    when u.banned_until is not null and u.banned_until > now() then 'BANNED'
    when u.deleted_at is not null then 'DELETED'
    when p.user_id <> u.id then 'PROFILE_USER_ID_DRIFT'
    else 'OK'
  end as status
from public.profiles p
left join auth.users u on u.id = p.user_id;

-- Lock down: only owner/staff/admin roles can read
revoke all on public.student_code_status from public;
revoke all on public.student_code_status from authenticated;
grant select on public.student_code_status to service_role;
-- Add RLS-style grant for staff via your existing role machinery if desired.
```
